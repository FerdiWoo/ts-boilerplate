# Drizzle Schema Conventions

Build the smallest schema that supports the confirmed product requirements. Treat
`table1` and `table2` as temporary discovery markers, not deployable table names.

## Before editing

1. Read `src/server/db/schema`, the relevant feature contracts, and existing
   migrations.
   Use `src/server/db/templates/table1.ts.example` and `table2.ts.example` as
   starting shapes when the product schema has not been designed yet.
2. Confirm the entities, relationships, ownership rules, deletion behavior, and
   query patterns. Do not invent product fields to make a placeholder look complete.
3. Replace placeholder names throughout schema, repositories, services, tests,
   and migrations before calling the feature complete. `npm run
check:placeholders` enforces this outside the intentional template directory.

## Application table conventions

- Put each cohesive domain's tables in `src/server/db/schema/<domain>.ts` and
  export them from `src/server/db/schema/index.ts`.
- Use singular `snake_case` SQL table names and `snake_case` SQL column names.
- Give ordinary application entities a UUID primary key generated by Postgres:

```ts
id: uuid('entity_id').primaryKey().defaultRandom();
```

- Use UUID foreign keys for references to application entities. Make ownership
  and required relationships explicit with `notNull()` and an intentional
  `onDelete` action.
- Use a composite primary key for a pure join table unless the relationship
  itself needs an addressable lifecycle or audit history.
- Use timezone-aware timestamps. New mutable entities normally include:

```ts
createdAt: timestamp('created_at', { withTimezone: true })
  .defaultNow()
  .notNull(),
updatedAt: timestamp('updated_at', { withTimezone: true })
  .defaultNow()
  .notNull(),
```

- Add `deletedAt` only when the product requires restore, retention, audit, or
  referential-history behavior. Otherwise prefer real deletion.
- Put shared PostgreSQL enums in `src/server/db/schema/_enum.ts`. Use a check or
  plain text only when values are intentionally open-ended.
- Add unique constraints for business identity and indexes for actual lookup,
  filtering, joining, and ordering paths. Avoid speculative indexes.
- Define Drizzle relations when the relational query API needs them. Relations do
  not replace database foreign keys.

## Boundary rules

- Schema and Drizzle imports remain server-only.
- Repositories own queries and transactions; services own business rules and
  authorization; actions and route handlers own transport validation.
- Return explicit DTOs/contracts across browser boundaries rather than raw
  Drizzle rows.
- Keep a complete business operation inside one transaction when partial writes
  would be invalid.

## Auth exception

Better Auth and other identity providers may require text identifiers and exact
table shapes. Generate those schemas with the provider's compatible CLI and do
not convert their IDs to UUIDs merely to match application tables. Link
application-owned profile data to the generated user identifier deliberately.

## Finish the change

1. Generate and inspect a named migration with `npm run db:generate -- --name <name>`.
2. Commit the SQL and Drizzle metadata together.
3. Run formatting, linting, type checks, unit tests, and relevant database-backed
   integration tests.
4. Run `npm run check:placeholders`; production builds run the same hard guard.
5. Use `db:push` only for disposable development databases; use reviewed
   migrations for shared and production environments.
